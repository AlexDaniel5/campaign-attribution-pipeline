# Campaign Attribution Pipeline

An end-to-end analytics-engineering project that models multi-touch
marketing attribution and a demand-generation funnel on top of
synthetic, Salesforce- and Marketo-shaped CRM data.

Stack: Python, SQL, dbt, DuckDB, pytest, GitHub Actions.

> All data in this project is SYNTHETIC. It is generated by a seeded
> Python generator and contains no real company, person, or account
> data. Company and person names are deliberately fictional.

## What it does

1. A Python generator creates internally consistent CRM objects
   (campaigns, leads, contacts, campaign members, opportunities) and
   loads them into a DuckDB warehouse as a `raw` schema.
2. dbt transforms the data through a layered ELT flow:
   `raw -> staging -> intermediate -> marts`.
3. Five attribution marts credit campaigns for each opportunity using
   different models (first-touch, last-touch, linear, time-decay,
   W-shaped). Credit always sums to 1.0 per opportunity.
4. A demand-generation funnel mart reports lead -> MQL -> opportunity
   -> closed-won counts and conversion rates per campaign.
5. dbt data-quality tests (73 total) and a pytest suite (15 tests)
   validate keys, referential integrity, accepted values, and the
   attribution/funnel invariants.
6. GitHub Actions CI builds the warehouse, runs `dbt build`, and runs
   pytest on every push and pull request.

## Architecture

```

                        (ordered touch sequence per opportunity,

     fct_attribution_first_touch                     fct_campaign_funnel
```

### Data model (raw / staging)

| Object            | Grain                        | Key columns                                   |
| ----------------- | ---------------------------- | --------------------------------------------- |
| campaigns         | one row per campaign         | campaign_id                                   |
| leads             | one row per lead             | lead_id, is_mql, is_converted                 |
| contacts          | one row per converted lead   | contact_id, lead_id                           |
| campaign_members  | one row per touch (event)    | campaign_member_id, campaign_id, lead_id      |
| opportunities     | one row per opportunity      | opportunity_id, contact_id, amount_usd, stage |

Referential chain:
`opportunity -> contact -> lead -> campaign_member -> campaign`.
Every opportunity therefore traces back to the campaign touches that
influenced it. The generator guarantees that every opportunity's lead
has at least one campaign touch dated on or before the opportunity
close date, so no pipeline is ever dropped during attribution.

### The attribution touch model

`int_opportunity_touches` is the shared input for all five attribution
marts. For each opportunity it collects the campaign-member touches of
the converting lead (dated on or before close) and uses SQL window
functions to compute, per touch:

- `touch_rank` -- position in the sequence (`row_number() over (...)`)
- `total_touches` -- number of touches on the opportunity (`count(*) over (...)`)
- `days_to_close` -- days between the touch and the opportunity close date

Each attribution mart then assigns a raw weight per touch and
normalizes by the per-opportunity sum of weights
(`raw_weight / sum(raw_weight) over (partition by opportunity_id)`),
which guarantees credit sums to 1.0.

## The five attribution methods

All methods distribute 1.0 of credit across an opportunity's touches;
`credited_amount = credit * opportunity amount`.

- First-touch: 100% of credit to the earliest touch. Answers "what
  created demand?"
- Last-touch: 100% of credit to the final touch before close. Answers
  "what closed the deal?"
- Linear: credit split evenly across every touch (`1 / total_touches`).
  A neutral baseline that treats all touches equally.
- Time-decay: touches closer to close earn exponentially more credit,
  using a 7-day half-life (`weight = 2 ^ (-days_to_close / 7)`).
  Rewards late-stage, deal-advancing touches.
- W-shaped: the three anchor touches -- first, middle, and last --
  each get a heavy weight (3) and the rest get a light weight (1).
  After normalization this yields the classic ~30/30/30 split across
  the anchors with the remainder shared by the middle touches. Credits
  both demand creation and deal closing while still valuing the middle.

Because credit sums to 1.0 per opportunity, the total credited pipeline
in every model reconciles exactly to the total opportunity pipeline --
this is enforced by singular dbt tests.

## Demand-generation funnel

`fct_campaign_funnel` reports, per campaign, the distinct leads that
reached each stage and the stage-to-stage conversion rates:

`lead -> MQL -> opportunity -> closed-won`

The generator makes every converted lead an MQL, so the counts are
monotonically non-increasing; a singular test asserts this.

## How to run it

Requires Python 3.9+ (CI uses 3.12).

```bash
# 1. Create a virtualenv and install dependencies
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Point dbt at the repo profile and the DuckDB file
export DBT_PROFILES_DIR="$PWD"
export DUCKDB_PATH="$PWD/warehouse.duckdb"

# 3. Generate synthetic data and load the raw schema
python -m campaign_attribution.build_warehouse --db "$DUCKDB_PATH" --seed 42

# 4. Build models and run data-quality tests
dbt build

# 5. Run the Python unit tests
python -m pytest
```

Or use the Makefile:

```bash
make install     # pip install -r requirements.txt
make warehouse   # generate + load synthetic raw data
make all         # warehouse + dbt build + dbt tests + pytest
make clean       # remove the warehouse and dbt artifacts
```

## Testing

- dbt: 73 data tests -- `not_null` / `unique` / `relationships` on
  keys, `accepted_values` on categorical columns, plus 11 singular
  custom tests that assert (a) attribution credit sums to 1.0 per
  opportunity in all five models and (b) total credited pipeline
  reconciles to total opportunity pipeline in all five models, plus a
  funnel monotonicity check.
- pytest: 15 tests covering schema shape, referential integrity, row
  counts, controlled vocabularies, generator determinism, and the
  invariants the generator must uphold.

```bash
dbt test            # 73 data tests
python -m pytest     # 15 tests
```
